# MiNote 제품·기술 개발 계획

작성일: 2026-09-26  
상태: 검토용 계획 초안. 제품 범위와 개발 순서를 제안하는 문서이며, 구현이 완료되었거나 기술 검증을 통과했다는 의미는 아니다.

## 1. 목표와 확정된 방향

MiNote는 학습과 업무에 모두 사용할 수 있는 손글씨 노트·PDF 주석 앱이다. Goodnotes의 주요 기능을 장기 목표로 삼고, 아이패드에서 필기 경험을 먼저 완성한 뒤 다른 플랫폼으로 확장한다.

사용자가 확정한 요구사항:

- 지원 목표: iPad, iPhone, macOS, Windows, Android.
- 첫 개발 대상: iPad.
- 용도: 학습과 업무를 비슷하게 지원하는 범용 앱.
- 우선순위: 아이패드 필기 품질. 다른 플랫폼은 순차 출시.
- 기능 목표: 노트 필기와 PDF 가져오기를 포함한 Goodnotes의 주요 기능 대부분.
- 현재 작업 범위: 계획 수립.

저장소 확인 결과: 기존 코드·설정·커밋이 없는 초기 저장소다. 기존 프레임워크에 맞춰야 하는 제약은 없다.

이 계획에서 제안하는 기본값:

- 첫 베타는 로그인 없이 오프라인으로 사용할 수 있다.
- 한국어·영어 입력을 고려하고, 화면 문구는 다국어로 확장할 수 있게 분리한다.
- 같은 문서를 모든 지원 플랫폼에서 읽고 편집하는 것을 장기 호환성 기준으로 삼는다.
- 브랜드·화면 구성은 MiNote에 맞게 설계한다. 기능 범위의 기준은 Goodnotes 공식 자료로 관리한다.
- 초기에는 페이지 기반 노트에 집중한다. 무한 캔버스는 후속 문서 유형으로 다룬다.

## 2. 성공 기준과 주요 사용자 흐름

### 학습

강의 PDF 가져오기 → 펜·형광펜으로 필기 → 빈 페이지 추가 → 중요한 페이지 표시 → 필기한 PDF 제출·공유.

### 업무

회의 노트 만들기 → 손글씨·텍스트·이미지로 기록 → 검토할 PDF에 의견 표시 → 폴더로 정리 → 다음 회의에서 다시 열기 → PDF 공유.

첫 베타의 성공 기준은 두 흐름이 인터넷 없이 완료되고, 앱을 닫았다 다시 열어도 저장된 기록과 위치가 유지되는 것이다. 후속 버전에서는 녹음·손글씨 검색·다른 기기에서 이어 쓰기를 추가한다.

## 3. 전체 기능 범위

아래 항목은 MiNote의 제안 범위다. Goodnotes는 운영체제와 요금제에 따라 기능이 다르므로, ‘모든 플랫폼의 모든 기능을 첫 출시부터 제공’하는 의미로 해석하지 않는다. 최신 기능 범주는 [Goodnotes 공식 기능 비교](https://support.goodnotes.com/hc/en-us/articles/13808767840015-Compare-Goodnotes-Plans-and-Features)를 참고했다.

| 기능군 | 첫 iPad 베타 | 후속 목표 |
| --- | --- | --- |
| 기본 필기 | 펜, 형광펜, 굵기·색상, 획 지우개, 실행 취소·다시 실행 | 다양한 브러시, 부분 지우개, 즐겨찾는 도구, 필기 제스처 |
| 입력·탐색 | Apple Pencil, 손바닥 오입력 방지, 손가락 스크롤·핀치 확대, 읽기 모드 | Pencil 기종별 버튼·호버 등, 사용자 제스처 설정 |
| 객체 편집 | 올가미로 획 선택·이동·삭제, 텍스트 상자, 이미지 삽입·이동·크기 변경 | 혼합 객체 선택, 복사·복제·회전, 이미지 자르기, 레이어 순서 |
| 도형 | 베타에서는 자유 필기로 작성 | 직선·사각형·원·화살표, 자동 보정, 자 |
| 노트 | 표지, 줄·격자·빈 용지, 다중 페이지 | 사용자 템플릿, 다양한 크기·배경, 템플릿 모음 |
| 페이지 | 추가·삭제·복제·재정렬, 썸네일, 책갈피 | 회전, 문서 간 이동, 사용자 목차, 페이지·문서 링크 |
| 자료 가져오기 | PDF, PNG/JPEG, 파일 앱·공유 메뉴 연동 | 카메라 스캔, 지원 이미지 확대, Office 파일의 PDF 변환 경로 |
| PDF 작업 | 원본 표시, 필기·강조, 확대, 텍스트가 있는 PDF의 검색·링크 탐색 | 선택 텍스트 강조, 주석·댓글 목록, PDF 목차, 암호 문서 처리 |
| 라이브러리 | 폴더, 이름 변경, 정렬, 최근 문서, 즐겨찾기, 휴지통 | 태그, 일괄 작업, 스마트 분류 |
| 검색 | 제목·폴더 검색, 열린 PDF의 기존 텍스트 검색 | 전체 문서 본문 검색, 손글씨 검색, 스캔 OCR, 결과 위치 표시 |
| 내보내기 | 필기 포함 PDF, 편집 원본인 `.minote` 백업·복원 | 이미지, 선택 페이지, 표준 PDF 주석, 인식 텍스트 포함 PDF |
| 저장 | 자동 저장, 오프라인, 실패 표시·재시도, 수동 백업·복원 | 자동 백업, 버전 이력·복구 |
| 생산성 | 가로·세로 화면 대응, 기본 키보드 입력 | 문서 탭, 다중 창, 화면 분할, 단축키, 프레젠테이션·레이저 포인터 |
| 손글씨 인식 | 후속 개발 | 한국어·영어 검색·텍스트 변환, 언어별 품질 측정 |
| 녹음 | 후속 개발 | 녹음·재생, 필기 시점 연동, 녹음 중단 복구 |
| 여러 기기 | 문서 포맷 호환성 검증 | 계정, 증분 동기화, 충돌 보존, 다섯 플랫폼 편집 |
| 협업 | 후속 개발 | 공개·비공개 공유, 권한, 댓글, 실시간 공동 편집 |
| 확장 도구 | 후속 개발 | 스티커·재사용 요소, 암기 카드·간격 반복, 화이트보드, 텍스트 문서 |
| AI | 후속 개발 | 문서 질의응답, 요약, 퀴즈, 녹음 전사·회의 요약, 수학 보조 |

검색은 **기존 PDF 텍스트 검색 / 이미지 OCR / 손글씨 인식**을 서로 다른 기능으로 관리한다. Goodnotes도 가져온 PDF에 OCR 층을 사후 생성하지 않는다고 안내하므로, PDF 가져오기만으로 스캔 자료까지 검색된다고 약속하지 않는다. [Goodnotes 검색 범위](https://support.goodnotes.com/hc/en-us/articles/7353743594127-How-to-Search-Your-Notes)

`.goodnotes` 파일의 직접 가져오기는 호환성을 별도 조사할 항목이다. 초기 이전 경로는 Goodnotes 등에서 PDF로 내보내 MiNote에 가져오는 방식이며, 이때 원래의 개별 획·녹음·편집 이력이 이전된다고 보장하지 않는다.

## 4. 기술 접근 비교와 추천

| 접근 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| iPad 네이티브 + 공통 문서 형식 | Apple Pencil·파일·PDF 경험을 우선 검증하기 좋음 | Android·Windows 편집기와 UI는 별도 구현 필요 | 사용자 우선순위에 가장 적합 |
| Flutter 공통 UI + 플랫폼별 필기 뷰 | 라이브러리·설정·일반 화면의 코드 공유에 유리 | 필기 뷰와 제스처·오버레이 결합을 별도 검증해야 함 | 출시 간격 최소화가 더 중요해지면 재검토 |
| 공통 자체 필기 엔진 + 여러 플랫폼 UI | 브러시 표현·편집 동작을 직접 통제 가능 | 입력·렌더링·브러시·접근성까지 초기 구현 부담이 큼 | 네이티브 접근의 검증 실패 시 범위를 좁혀 도입 |

추천 구성:

- 앱 화면: **SwiftUI**.
- 필기·제스처가 집중되는 편집 영역: **UIKit + PencilKit** 우선 검증.
- PDF 표시와 페이지 작업: **PDFKit** 우선 검증.
- 로컬 메타데이터: **SQLite 기반 저장소**. 구체 라이브러리는 구현 명세에서 선택.
- 문서 본문과 첨부: 앱 내부 문서 디렉터리. 휴대용 `.minote` 패키지로 내보내기.
- OCR·필기 인식: 인식 엔진을 교체할 수 있는 인터페이스 뒤에 배치.
- 서버: 첫 로컬 베타 이후 별도 설계. 플랫폼 공통 계정·메타데이터 API·객체 저장소가 후보 구성.

Apple은 PDF 페이지 위에 편집 뷰를 올리고 PencilKit과 결합하는 방식을 제공한다. 다만 오버레이 화면만 구현해서는 저장·내보내기까지 해결되지 않으므로 별도의 문서 모델이 필요하다. [Apple PDFKit 설명](https://developer.apple.com/videos/play/wwdc2022/10089/)

Flutter도 네이티브 iOS 뷰를 삽입할 수 있다. 따라서 Flutter를 ‘필기가 불가능한 기술’로 제외하는 것이 아니라, 이번에는 iPad 품질이 우선이라는 제품 판단으로 네이티브를 추천한다. [Flutter 플랫폼 뷰](https://docs.flutter.dev/platform-integration/ios/platform-views)

이 구성은 다섯 플랫폼 앱의 코드가 자동으로 공유된다는 뜻이 아니다. **공유 대상은 먼저 문서 규격·편집 의미·호환성 테스트이며**, 실제 공통 코어를 Rust·Kotlin 등으로 추출할지는 두 번째 플랫폼 검증 이후 결정한다.

## 5. 문서·저장 아키텍처

### 모듈 경계

| 모듈 | 책임 | 다른 모듈과의 경계 |
| --- | --- | --- |
| Library | 폴더·문서 목록·즐겨찾기·휴지통 | 문서 ID와 메타데이터만 사용 |
| Editor | 도구 상태·선택·편집 명령·실행 취소 | 화면 좌표를 문서 좌표로 변환해 명령 전달 |
| Document Model | 페이지·획·텍스트·이미지·순서·버전 규칙 | 운영체제 UI 타입을 저장 규격에 포함하지 않음 |
| Ink Adapter | Pencil 입력·표시와 공통 획 모델 사이 변환 | 브러시·획 변환의 손실 여부를 보고 |
| PDF Adapter | 원본 렌더링·검색·좌표 변환·PDF 출력 | 원본 PDF와 MiNote 객체를 분리 |
| Persistence | 저장·저널·복구·마이그레이션·백업 | 저장 성공 여부와 문서 리비전 반환 |
| Search / Audio | 인덱싱·인식, 녹음과 시점 연동 | 필기 경로를 막지 않는 별도 작업 |
| Sync | 계정·전송·재시도·경합 처리 | 로컬 편집 명령·리비전·첨부 ID 이용 |

### 공통 문서 형식의 원칙

- 문서·페이지·획·텍스트·이미지에 안정적인 ID를 부여한다.
- 객체 리비전·편집 명령 ID·삭제 기록을 정의한다. 동기화를 도입할 때 부모 페이지와 첨부의 관계까지 추적할 수 있어야 한다.
- 페이지 크기와 객체 좌표는 화면 픽셀이 아닌 문서 단위로 보존한다. 제안 규칙은 1/72인치 단위, 페이지 좌상단 원점이다.
- PDF의 좌표계·crop box·회전을 변환하는 규칙을 별도 정의한다. 화면 확대·회전 후에도 필기 위치가 바뀌지 않아야 한다.
- 획에는 경로 또는 샘플, 시간, 지원되는 압력·기울기, 색상·굵기·도구 종류, 변환·잘림 정보, 렌더링 버전을 기록한다.
- 텍스트는 내용·스타일·상자 위치를, 이미지는 첨부 ID·위치·크기·변환을 기록한다.
- 글꼴이 없는 플랫폼에서의 대체 규칙과 텍스트 상자 넘침 처리도 교환 규격에 포함한다.
- 원본 PDF·이미지는 첨부로 유지하고 페이지가 원본 페이지를 참조한다. 편집마다 큰 PDF 전체를 복사하지 않는다.
- 스키마 버전과 단계별 마이그레이션을 둔다. 구버전 앱은 이해하지 못하는 객체를 조용히 지우지 않고 보존하거나 읽기 전용으로 연다.
- 검색 인덱스와 썸네일은 재생성 가능한 데이터로 취급한다.

**PencilKit 원본 바이트를 유일한 문서 원본으로 사용하지 않는다.** Apple 내 재열기를 위한 보조 캐시로 보관할 수 있지만, 공통 형식이 핵심 편집 내용을 재구성할 수 있어야 한다. 두 표현의 리비전이 다르면 캐시를 다시 만든다.

모든 PencilKit 브러시가 타 플랫폼에서 똑같이 재현된다고 가정하지 않는다. 초기 검증에서 기본 펜·형광펜·지우기·선택 이동의 왕복 변환을 확인하고, 실패하면 브러시 범위를 제한하거나 해당 기능의 렌더러를 직접 구현한다. 압력·마스크·부분 삭제·변형까지 검증되기 전에는 완전한 무손실 호환을 선언하지 않는다.

### 저장과 복구

입력 → 메모리상 편집 명령 → 로컬 저널·첨부 기록 → 저장 완료 표시 → 백그라운드 스냅샷·검색 인덱싱 순서로 설계한다. 이후 동기화는 저장된 변경을 전송한다.

- 첫 버전에서는 같은 문서를 동시에 쓰는 편집 세션을 하나로 제한한다. 다중 창 쓰기는 충돌 규칙을 도입한 뒤 연다.
- 저장 완료 표시는 디스크 기록 성공 이후에만 표시한다. 실패 시 기록을 유지하고 재시도·다른 위치로 내보내기를 제공한다.
- 문서 저장 도중 강제 종료해도 마지막 완료 리비전으로 복구해야 한다.
- 메타데이터와 첨부 간 중간 실패를 복구할 수 있도록 저널·해시·원자적 교체 경계를 정의한다.
- 휴지통 복원, 다른 설치로의 백업 복원을 실제로 검증한다. 서버 동기화와 백업은 별도 기능으로 유지한다.
- 큰 파일은 진행률·취소를 제공하고, 손상·잠긴 PDF·저장 공간 부족이 기존 노트를 손상시키지 않아야 한다.

### 내보내기 계약

첫 베타는 편집용 `.minote` 백업과 배포용 PDF를 제공한다. PDF는 원본 페이지 위에 표시 결과를 합성하는 방식으로 검증하며, 지원되는 원본 텍스트·링크 보존과 주석 외관을 테스트한다. 보존하지 못하는 항목은 내보내기 화면에서 알려준다.

표준 PDF 주석 출력과 손글씨 인식 텍스트 삽입은 후속 단계다. 외부 PDF 뷰어에서 움직일 수 있는 주석과 MiNote에서 브러시까지 다시 편집하는 원본은 서로 다른 호환성 수준이다. Goodnotes도 내보내기 유형에 따라 편집성·검색·링크 보존에 차이를 두고 있다. [Goodnotes PDF 내보내기](https://support.goodnotes.com/hc/en-us/articles/8537070839183-Choose-Between-Editable-and-Flattened-PDF-Export)

## 6. 단계별 개발 순서

### 0단계 — 필기·문서 호환성 기술 검증

산출물: 실기기 시험용 편집기, 샘플 문서, 성능 기록, 기술 선택 기록. 제품 출시 단계가 아니다.

- 빈 페이지·PDF에 필기하고 확대·스크롤·지우기·다시 실행을 시험한다.
- 공통 형식으로 저장하고 다시 불러온 뒤 위치·브러시·편집 가능성을 확인한다.
- Apple 외의 독립 렌더러 또는 최소 Android/Windows 시험 앱으로 기본 획을 읽고 수정한 뒤 iPad에서 다시 연다. 단순 이미지 출력만으로 이 검증을 통과시키지 않는다.
- 가장 오래된 지원 후보 iPad와 고주사율 iPad에서 지연·메모리·페이지 전환을 측정한다.
- 통과하지 못하면 UI 개발을 확대하기 전에 필기 어댑터·저장 규격·기술 선택을 수정한다.

### 1단계 — 로컬 노트 기반

산출물: 빈 노트를 만들고 필기한 뒤 안전하게 다시 열 수 있는 앱.

- 앱 기본 구조, 라이브러리, 노트·폴더, 기본 용지, 페이지 추가.
- 기본 펜·형광펜·획 지우개·실행 취소.
- 문서 모델·로컬 저장·복구·스키마 버전.
- 글자·도구 버튼의 접근성, 가로·세로 대응, 한국어 입력 기반.

### 2단계 — 필기와 PDF를 결합한 편집기

산출물: 학습과 업무의 두 핵심 흐름을 끝까지 수행하는 앱.

- PDF·이미지 가져오기, PDF 원본을 유지한 필기 레이어.
- 올가미, 텍스트·이미지 객체, 페이지 관리·책갈피.
- PDF 기존 텍스트 검색, 문서 제목 검색.
- 필기 포함 PDF와 `.minote` 내보내기·복원.
- 대용량 자료·저장 공간 부족·가져오기 취소 처리.
- 베타 저장 규격을 고정하기 전, 독립 렌더러에서 텍스트·이미지·PDF 오버레이·페이지 재정렬과 삭제를 왕복 검증한다. 구버전에서 모르는 객체를 보존하는 시험도 포함한다.

### 3단계 — iPad 실사용 베타

산출물: 핵심 기능 표의 ‘첫 iPad 베타’를 충족하는 검증 빌드.

- 폴더·즐겨찾기·휴지통 등 라이브러리 마감.
- 장시간 필기, 파일 호환, 강제 종료·복구, 접근성·화면 회전 점검.
- 학습 자료와 업무 문서 각각으로 사용성 시험.
- 서명·배포 환경을 준비한 뒤 테스트 배포. 배포 계정 준비 여부를 일정에 반영.

### 4단계 — iPad 고급 기능과 Apple 플랫폼 확장

산출물은 독립적으로 나눠 출시한다.

- 생산성 묶음: 도형, 부분 지우기, 고급 올가미, 템플릿, 탭·다중 창, 단축키.
- 검색 묶음: 전체 본문 색인, 한국어·영어 필기 검색·변환, 스캔 OCR.
- 녹음 묶음: 녹음·필기 시점 연결, 중단·복구, 재생.
- iPhone: 같은 문서를 작은 화면에서 읽고 정리하며 텍스트·터치로 편집.
- macOS: 같은 문서 모델을 사용하고 키보드·마우스·트랙패드 편집을 최적화. Catalyst와 네이티브 UI의 실제 사용성을 비교해 선택.

OCR 엔진은 언어·OS별 품질을 측정한 뒤 선택한다. 이미지용 Vision OCR과 획 데이터용 ML Kit는 입력 방식이 다르다. ML Kit의 디지털 잉크 인식은 iOS·Android에서 기기 내 처리를 지원한다. [Apple Vision](https://developer.apple.com/documentation/vision/recognizing-text-in-images), [Google ML Kit](https://developers.google.com/ml-kit/vision/digital-ink-recognition)

Apple이 WWDC26에서 소개한 OS 27의 PencilKit 필기 인식·경로 변환 기능은 선택적으로 검토한다. 최소 지원 OS에서 쓸 수 있는지와 한국어 품질을 확인하기 전에는 핵심 기능의 필수 의존성으로 삼지 않는다. [Apple PencilKit 신규 기능](https://developer.apple.com/videos/play/wwdc2026/203/)

### 5단계 — 여러 기기 동기화와 Android·Windows

산출물: 공통 문서를 여러 기기에서 이어 편집하는 서비스.

- 공통 계정·문서 메타데이터·첨부 저장소, 증분 업로드·다운로드, 재시도.
- 의존관계가 없는 객체 수정은 병합하고, 같은 객체의 동시 변경·삭제 충돌은 양쪽 기록을 보존한다. 조용한 최종 저장 덮어쓰기는 금지한다.
- 페이지 삭제와 그 페이지의 새 필기가 충돌하면 삭제 기록과 편집된 복구 사본을 함께 남긴다. 동시 페이지 재정렬은 순서 충돌로 다루고 두 순서를 기록한다. 참조 중이거나 미동기화 변경에 필요한 첨부는 바로 영구 삭제하지 않는다.
- 객체 리비전·삭제 기록·변경의 선후 관계와 위 복합 충돌 규칙을 동기화 명세에서 확정하고, 여러 기기에서 결과가 같아지는지 테스트한다.
- 연결 끊김, 중복 전송, 업로드 중 종료, 시간 차이, 삭제 후 재연결을 테스트한다.
- iPad와 iPhone/macOS에서 동기화를 먼저 검증하고 동일 API를 Android·Windows로 확장한다.
- Android는 스타일러스와 터치, Windows는 펜·마우스·키보드 입력을 검증한다. 최종 목표에는 두 플랫폼의 편집 기능도 포함한다.
- 초기 기술 검증 결과를 이용해 플랫폼별 UI와 공통 코어의 실제 공유 범위를 결정한다.

동기화 설계는 4단계와 병행할 수 있다. 고급 기능 전체 완성을 다른 플랫폼 개발의 선행 조건으로 삼지 않는다. iCloud 전용 문서 구조에 묶이지 않도록 백엔드와 로컬 모델을 분리한다.

### 6단계 — 공동 작업과 확장 기능

- 권한·공유·댓글 → 동시 편집 프로토콜 → 실시간 공동 편집 순으로 개발.
- AI 요약·질의응답·전사·퀴즈는 문서 검색과 녹음 기반이 준비된 뒤 도입.
- 화이트보드·블록형 문서·암기 카드는 각각 별도 명세와 출시 단위로 개발.
- 자동 외부 백업, 외부 서비스 연동, 요금제·저장 한도는 운영 계획과 함께 설계.
- 로컬 노트는 기본적으로 기기 내에 유지하고, 서버 기능 사용 시 업로드 범위와 삭제·복구 동작을 제품 흐름에 명시한다.

## 7. 플랫폼 확장 순서

**제품 출시 기본 순서: iPad → iPhone → macOS → Android → Windows.**

Android와 Windows의 순서는 실사용 수요·개발 인력에 따라 바꿀 수 있다. 두 플랫폼의 문서 호환성 검증은 0단계부터 시작한다. 플랫폼 출시를 늦추는 것과 문서 호환성 설계를 늦추는 것을 구분한다.

모든 플랫폼은 같은 문서의 읽기·기본 편집·PDF 가져오기·내보내기를 공통 목표로 가진다. 펜이 없는 장치에서는 마우스·키보드·터치에 맞는 입력을 제공하며, UI를 단순 확대·축소하지 않는다.

## 9. 일정과 자원

확정 납기 대신 초기 범위 추정치를 사용한다. **숙련된 Apple 플랫폼 개발자 1명이 전담하고 단순한 디자인으로 시작하는 경우**, 0~3단계의 로컬 iPad 베타는 약 **12~20주**를 첫 추정치로 둔다. 이 추정에는 최소 독립 렌더러를 통한 문서 호환성 시험도 포함한다.

| 범위 | 추정 |
| --- | --- |
| 0단계 기술 검증 | 2~4주 |
| 1단계 노트·저장 기반 | 3~5주 |
| 2단계 PDF·편집 완성 | 5~7주 |
| 3단계 베타 검증·안정화 | 2~4주 |

이 추정에는 OCR·녹음·동기화·다른 플랫폼의 제품 앱·실시간 협업·AI가 포함되지 않는다. 독립 렌더러 구현에 추가 학습이 필요하거나 공통 필기 변환이 실패해 자체 엔진이 필요해지면 다시 산정한다. 공개 출시 준비와 베타 이후 개선 기간도 별도다.

전체 Goodnotes 기능군과 다섯 플랫폼 완성은 여러 릴리스에 걸친 장기 개발이다. 인력·품질 기준·클라우드 예산이 정해지지 않은 현재 시점에 전체 완료일을 고정하지 않는다.

필요 자원은 개발용 Mac·Xcode, 검증용 iPad·Pencil, 테스트 배포 환경이다. 확장 단계에는 실제 Android 펜 장치와 Windows PC·펜 장치가 필요하다. SDK 라이선스·서버·저장·인식·AI 비용은 해당 단계 진입 전에 비교한다.

환경 점검 중 시스템 개발 도구가 Xcode 라이선스 미동의 메시지를 반환했다. 문서 작성은 가능했으며, 실제 빌드 검증에 들어가기 전에 사용자가 해당 약관을 검토·동의하고 도구가 정상 실행되는지 확인해야 한다.

## 10. 다음 설계 단위와 결정 시점

하나의 거대한 구현 계획으로 진행하지 않고 다음 단위별로 설계·구현·검증을 나눈다.

1. **첫 단위: iPad 필기·PDF·공통 문서 형식 기술 검증.** 시험 입력, 저장 계약, 왕복 편집, 장치별 측정 기준을 명세한다.
2. 로컬 문서 저장·복구와 라이브러리.
3. PDF 기반 편집기와 내보내기.
4. 검색·OCR, 녹음, 고급 편집 기능 각각.
5. 플랫폼별 앱과 공통 동기화.
6. 협업·AI·추가 문서 유형 각각.
